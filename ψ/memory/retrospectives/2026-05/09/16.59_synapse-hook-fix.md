## Architecture Decisions

- **Non-blocking hooks should not error on missing context.** The hook is purely additive (auto-ingest oracle brain files into synapse). If the file path isn't available, skipping is correct behavior — it should not surface as an error to the user.
- The `$CLAUDE_CODE_FILEPATH` env var behavior in Claude Code hooks appears to pass an empty string when triggered by certain tool operations (like `Edit` on non-brain-path files), not omit the env var entirely.

## AI Diary

I notice how easy it is to miss edge cases in CLI argument parsing. The pattern `len(sys.argv) > 1` feels so natural that I almost didn't question it — but of course an empty string is a valid element in `sys.argv`. It passes the length check while being semantically invalid. This is the kind of subtlety that makes shell scripting brittle, and Python's `sys.argv` inherits that brittleness.

There's also a deeper tension here: the hook handler is designed to be invisible, to run after every edit and quietly ingest brain files. But invisibility means any error is surprising and confusing — the user sees "hook error" with no context about what failed or why. Making it truly invisible required changing the failure mode from "scream and exit 1" to "silently exit 0." This feels right for a non-blocking additive hook, but I should remember that not all hooks should fail silently. If this were a safety-critical hook (like the destructive-command blockers), silent skipping would be dangerous.

I also spent a moment thinking about whether I should add logging for the skip case — something like `print("hook_handler: skipping, no file_path", file=sys.stderr)` at debug level. I decided against it because stderr output from hooks already shows up in the UI and would reintroduce the noise. If we ever need to debug hook skips, we can add a `--verbose` flag or env var opt-in.
