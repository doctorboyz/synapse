## AI Diary (150+ words)

I feel a mix of relief and embarrassment writing this. The user reported hook errors — two distinct failures — and both traced back to the same root cause: I (or a previous session) had renamed the module structure from `synapse/` to `src/` but left stale references in `settings.json`. It's a classic "refactored the code, forgot the config" mistake. What made it worse was that there were *two* ingest hooks registered, one pointing to a dead module and one that was technically correct but using the wrong Python binary and no working directory. So every file edit was triggering two hooks, one guaranteed to fail.

The fix was surgical: delete the dead hook, fix the MCP args, and prepend `cd` to the remaining hook so Python could resolve `src.ingest.hook_handler` relative to the project root. Testing showed the DB has 708 documents across 6 scopes, which means synapse has been working for other projects — just not for this repo because the hooks were broken. I also created a test file in `ψ/` to verify the remaining hook will auto-ingest on the next edit cycle.

What stings a little is that this error was visible in every session — the hook failure messages were showing up after every Write/Edit — but apparently got ignored or normalized until the user screenshotted it. That's a signal I need to treat non-blocking hook errors as actual problems, not background noise.

## Honest Feedback (100+ words, 3 friction points)

1. **Hook errors were invisible to me until the user pointed them out.** The "non-blocking status code" framing made the failures feel like warnings rather than real errors. I normalized them. That's on me — if a hook fails every single time, it's not a warning, it's a broken feature. I should have noticed the pattern and investigated earlier, not waited for a screenshot.

2. **Two ingest hooks is a sign of a messy migration.** The dead hook and the working hook coexisting meant the migration from `synapse/` to `src/` was incomplete. I didn't clean up the old entry. This is a recurring pattern: add the new thing, forget to remove the old thing. The result is confusing error messages and wasted compute.

3. **Hardcoded paths in settings.json are brittle.** The hook command references an absolute path to the venv Python and an absolute path to the project directory. If either moves, the hook breaks silently. A relative path or an environment variable would be more resilient. I should propose a `PROJECT_ROOT` env var or use `cd` with `$(git rev-parse --show-toplevel)` where possible.

## Lessons Learned

1. **Module rename ต้องจับทุก references** — ไม่ใช่แค่ source code แต่รวมถึง config, hooks, MCP args, และ documentation
2. **Hook "non-blocking" ≠ ไม่สำคัญ** — ถ้า hook fail ซ้ำๆ ต้อง investigate ทันที
3. **Test after config change** — แม้แค่ settings.json ก็ควร verify ว่า hook ยังทำงานได้
4. **Single source of truth สำหรับ paths** — ใช้ env vars หรือ relative paths แทน hardcoded absolute paths
