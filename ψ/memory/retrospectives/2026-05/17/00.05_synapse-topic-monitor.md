## Honest Feedback

**Friction 1: Reactive vs proactive reliability.** Every fix in this session was reactive. The user asked about reconcile history → I added it. The user asked why daemon crashes → I fixed it. A well-designed system should have these observability and resilience features from the start. I need to develop a mental checklist for daemon/service patterns before writing the first line.

**Friction 2: stdout is not logging.** Reconcile output went to `log.info()` which prints to stdout. In Docker, that goes to container logs — ephemeral and hard to query. For a system that runs daily jobs, persistent structured logs in the database (or at minimum a log file) are essential. I treated logging as debugging output when it should be operational telemetry.

**Friction 3: Docker restart policy absent.** The Dockerfile doesn't set `--restart`. If the Python process segfaults or OOMs, the container dies and stays dead. For a background service that users depend on for knowledge ingestion, this is a single point of failure. I should have added `restart: unless-stopped` to docker-compose.yml as part of the original Docker setup.

## Lessons Learned

1. **Every scheduled job needs an audit log** — not for debugging, but for answering "did it run? what happened?" User questions should be answerable from the database, not from log grepping.
2. **Daemon boot must be resilient** — external services (Ollama, Qdrant, PG) can be down. The daemon should start in degraded mode, not crash.
3. **PID file + signal handling are non-optional** — `status`, `stop`, `restart` commands depend on this. If it's missing, the CLI becomes a black box.
